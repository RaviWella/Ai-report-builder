# DataHub Setup Guide

This guide covers how to set up DataHub locally for the MintHRM Analytics project,
connect the warehouse PostgreSQL database, and keep metadata in sync when the database changes.

---

## Prerequisites

- Docker Desktop installed and running
- Python 3.11 or 3.12 installed via pyenv
- Local MySQL service running on port 3306 (conflict workaround required — see below)

---

## 2. Start DataHub (First Time)

DataHub uses Docker. Because port 3306 is already used by a local MySQL service,
the quickstart compose file must be patched to use port 3307 instead.

### Step 1 — Download the compose file

Run `datahub docker quickstart` once to download the images and compose file,
then immediately stop it when it fails on the port conflict:

```bash
datahub docker quickstart
# Ctrl+C after images finish downloading
datahub docker quickstart --stop
```

### Step 2 — Patch the MySQL port

```powershell
$file = "$env:USERPROFILE\.datahub\quickstart\docker-compose.yml"
$custom = "$env:USERPROFILE\.datahub\quickstart\docker-compose-custom.yml"
$content = Get-Content $file -Raw
$patched = $content -replace "published: '3306'", "published: '3307'"
Set-Content $custom -Value $patched -NoNewline
```

This creates a `docker-compose-custom.yml` with MySQL mapped to host port 3307
instead of 3306. The internal container communication still uses 3306 — only the
host binding changes.

### Step 3 — Start DataHub using the patched file

```powershell
$env:DATAHUB_VERSION = "v1.5.0.3"
$env:HOME = "$env:USERPROFILE"
$env:DATAHUB_TOKEN_SERVICE_SIGNING_KEY = "WnEdIeTG/VVCLQqGwC/BAkqyY0k+H8NEAtWGejrBI94="
$env:DATAHUB_TOKEN_SERVICE_SALT = "JWYLEe+XzkVW4Wiiigu1z9Vwm6jPHvEs"
$env:UI_INGESTION_DEFAULT_CLI_VERSION = "0.14.1.5"
$env:DATAHUB_MAPPED_GMS_PORT = "8080"
$env:DATAHUB_MAPPED_FRONTEND_PORT = "9002"

docker compose --profile quickstart `
  -f "$env:USERPROFILE\.datahub\quickstart\docker-compose-custom.yml" `
  -p datahub up -d
```

> **Note:** MySQL takes ~20 seconds to become healthy before the rest of the stack starts.
> If you see `datahub-mysql-1 is unhealthy`, wait 20 seconds and re-run the command above.

### Step 4 — Verify all containers are healthy

```powershell
docker ps --filter "name=datahub" --format "table {{.Names}}`t{{.Status}}"
```

Expected output — all containers should show `(healthy)`:

```
NAMES                              STATUS
datahub-datahub-gms-quickstart-1   Up 2 minutes (healthy)
datahub-frontend-quickstart-1      Up 2 minutes (healthy)
datahub-mysql-1                    Up 5 minutes (healthy)
datahub-kafka-broker-1             Up 5 minutes (healthy)
datahub-opensearch-1               Up 5 minutes (healthy)
```

## 3b. Secured DataHub (production / PAT)

When GMS authentication is enabled (typical production), MintHRM uses a **Personal Access Token (PAT)** for:

1. **Runtime** — datamart table search (`POST {DATAHUB_GMS_URL}/api/graphql` with `Authorization: Bearer …`)
2. **Ingestion** — `datahub ingest` sink `token:` (generated by refresh scripts from the same env var)

### Create a token in DataHub UI

1. Open the DataHub UI (e.g. `https://datahub.yourcompany.com` or local `http://localhost:9002`).
2. Sign in (default local quickstart: `datahub` / `datahub`).
3. **Settings → Access Tokens → Generate**.
4. Copy the token once (it is not shown again).

### Configure `backend/.env`

```env
DATAHUB_GMS_URL=https://datahub-gms.yourcompany.com
DATAHUB_GMS_TOKEN=eyJ...your-personal-access-token...
```

| Variable | Required when secured? | Notes |
|----------|----------------------|--------|
| `DATAHUB_GMS_URL` | Yes | GMS base URL **without** `/api/graphql` |
| `DATAHUB_GMS_TOKEN` | Yes | PAT from DataHub UI; omit for local no-auth quickstart |
| `DATAHUB_TIMEOUT_SECONDS` | No | Default `5` |

Restart the API after changing these values.

### Verify auth

```powershell
$token = "YOUR_PAT"
$body = '{"query":"{ __typename }"}'
Invoke-RestMethod -Method Post -Uri "https://datahub-gms.yourcompany.com/api/graphql" `
  -Headers @{ Authorization = "Bearer $token"; "Content-Type" = "application/json" } `
  -Body $body
```

Expect JSON with `"data"` — not HTTP 401.

### Re-ingest with token

```powershell
.\scripts\refresh_datamart_metadata.ps1
```

The script reads `DATAHUB_GMS_TOKEN` from `backend/.env` and writes it into `datahub_ingestion.generated.yml` (gitignored).

### Code touched in this repo

| File | Role |
|------|------|
| `backend/app/services/ai_services/datamart/config.py` | Reads `DATAHUB_GMS_TOKEN` |
| `backend/app/services/ai_services/datamart/datahub.py` | Sends `Authorization: Bearer` on GraphQL |
| `scripts/refresh_datamart_metadata.ps1` / `.sh` | Adds `token:` to generated ingestion recipe |
| `backend/.env.example`, `backend/.env.production.example` | Document env vars |

If `DATAHUB_GMS_TOKEN` is missing on a secured GMS, datamart **still runs** (catalog + warehouse introspection) but logs `DataHub rejected credentials (HTTP 401)`.

## 4. Connect the Warehouse Database

The ingestion recipe is in `datahub_ingestion.yml`. It connects to the warehouse
PostgreSQL database and ingests only the `public_mint_audit` schema.

### Current configuration (`datahub_ingestion.yml`)

```yaml
source:
  type: postgres
  config:
    host_port: "139.162.17.40:10000"
    database: "warehouse"
    username: "mint_bi_reader"
    password: "<password>"
    schema_pattern:
      allow:
        - "public_mint_audit"

sink:
  type: datahub-rest
  config:
    server: "http://localhost:8080"
```

### Run the ingestion

```bash
datahub ingest -c datahub_ingestion.yml
```

This pushes all table and column metadata from `public_mint_audit` into DataHub.
The first run takes ~20 seconds for 19 tables.

### Verify ingestion succeeded

```powershell
Invoke-RestMethod -Uri "http://localhost:8080/entities?action=search" `
  -Method Post -ContentType "application/json" `
  -Body '{"input":"public_mint_audit","entity":"dataset","start":0,"count":5}' |
  ConvertTo-Json -Depth 2
```

You should see `numEntities: 19` in the response.

## 5. Add more schemas (DataHub only)

To ingest additional PostgreSQL schemas into DataHub, extend `schema_pattern` in `datahub_ingestion.yml`:

```yaml
schema_pattern:
  allow:
    - "public_mint_audit"
    - "public_mint_reports"   # example: second schema
```

Then re-run:

```bash
datahub ingest -c datahub_ingestion.yml
```

> Ingesting a schema into DataHub does **not** make the Datamart agent query it automatically. You must also point the app warehouse config at that schema and update the semantic catalog (see **section 10**).

## 6. Keeping DataHub in Sync When the Database Changes

DataHub does not auto-sync. You must re-run ingestion manually whenever the database schema changes.

### When to re-run ingestion

| Database change | Action required |
|----------------|-----------------|
| New table added | Re-run ingestion |
| Column added or removed | Re-run ingestion |
| Table renamed or dropped | Re-run ingestion |
| Data changes only (no schema change) | No action needed |

### Re-run ingestion command

```bash
datahub ingest -c datahub_ingestion.yml
```

DataHub ingestion is **idempotent** — running it multiple times is safe. It updates
existing metadata and adds new entries without duplicating anything.

### Recommended: Schedule regular ingestion

For a production setup, schedule ingestion to run automatically. Example using
Windows Task Scheduler (run daily at midnight):

```powershell
$action = New-ScheduledTaskAction -Execute "datahub" -Argument "ingest -c C:\MintHRM Repo\mint-analytics\datahub_ingestion.yml"
$trigger = New-ScheduledTaskTrigger -Daily -At "00:00"
Register-ScheduledTask -TaskName "DataHub Ingestion" -Action $action -Trigger $trigger
```

Or on Linux/Mac with cron:

```bash
0 0 * * * datahub ingest -c /path/to/datahub_ingestion.yml >> /var/log/datahub_ingest.log 2>&1
```

### Stop

```powershell
$env:HOME = "$env:USERPROFILE"
docker compose --profile quickstart `
  -f "$env:USERPROFILE\.datahub\quickstart\docker-compose-custom.yml" `
  -p datahub stop
```

### Start again (data is preserved)

Re-run the Step 3 command from section 2. All previously ingested metadata is

### Full reset (wipe all data and start fresh)

```powershell
# Stop and remove containers + volumes
docker compose --profile quickstart `
  -f "$env:USERPROFILE\.datahub\quickstart\docker-compose-custom.yml" `
  -p datahub down -v

# Re-patch the compose file (volumes are gone, file stays)
$file = "$env:USERPROFILE\.datahub\quickstart\docker-compose.yml"
$custom = "$env:USERPROFILE\.datahub\quickstart\docker-compose-custom.yml"
$content = Get-Content $file -Raw
$patched = $content -replace "published: '3306'", "published: '3307'"
Set-Content $custom -Value $patched -NoNewline

# Start fresh
# (run the Step 3 command from section 2)

# Re-run ingestion after startup
datahub ingest -c datahub_ingestion.yml
```

## 8. Architecture: three layers (do not confuse them)

The Datamart SQL agent uses **three separate mechanisms**. They work together; none replaces the others.

| Layer | What it stores | Used for |
|-------|----------------|----------|
| **PostgreSQL warehouse** | Real tables, columns, data | SQL execution; **column allowlist** via live introspection |
| **DataHub** | Searchable metadata catalog (ingested from the DB) | **Table discovery** via keyword search |
| **`semantic_catalog.yaml`** | Curated business vocabulary (topics, synonyms, joins) | **Seed tables** + short “semantic guidance” in the LLM prompt |

```text
User question
    │
    ├─► DataHub search (keywords)     → candidate table names (URNs)
    ├─► semantic_catalog.yaml         → seed tables + synonym hints
    ├─► Warehouse table list + match  → ranked table names (fallback/boost)
    └─► Prior SQL in session          → tables already in context
                │
                ▼
        Merge (max ~5 tables) → introspect PostgreSQL → GROUNDED SCHEMA for LLM
```

**Important:** In the current code (`schema_broker.py`), **column names in the prompt come from PostgreSQL introspection**, not from DataHub. DataHub is used to help pick **which tables** to introspect. The function `get_columns_for_urns()` in `datahub.py` can fetch columns from DataHub, but the schema broker does not call it today.

If DataHub is down, the agent still works using semantic seeds + warehouse keyword ranking + introspection.

## 9. How ingestion extracts table and column metadata

When you run:

```bash
datahub ingest -c datahub_ingestion.yml
```

the **PostgreSQL source connector** (`type: postgres` in the recipe) connects to the warehouse with the credentials in the YAML file and reads metadata from the database catalog.

### What is extracted automatically

| Metadata | Source in PostgreSQL | Notes |
|----------|----------------------|--------|
| Database name | Connection config | e.g. `warehouse` |
| Schema names | Filtered by `schema_pattern.allow` | Only listed schemas are ingested |
| Table / view names | `information_schema` / catalog | One **dataset** per table in DataHub |
| Column names | Table metadata | Stored as schema fields on the dataset |
| Column types | Table metadata | e.g. `varchar`, `numeric`, `timestamp` |
| Table/column **comments** | `pg_description` (if present) | Only if you (or dbt) ran `COMMENT ON TABLE/COLUMN` in Postgres |

The default recipe does **not** run dbt or read Excel documentation. It reflects **what exists in the database catalog** at ingest time.

### What is *not* extracted unless you add it

- Business synonyms (“department” → `emp_section_id`) — **not** from Postgres; those live in `semantic_catalog.yaml` or DataHub Glossary (manual).
- Join rules — curated in `semantic_catalog.yaml` and `join_hints.py`.
- Row-level or sample data — not ingested by this recipe (metadata only).

### How descriptions improve search quality

DataHub’s search index can use names, tags, and descriptions. To make keyword search work better:

1. **Database comments** (picked up on re-ingest):
   ```sql
   COMMENT ON TABLE public_mint_audit.dim_employee IS 'Employee master dimension';
   COMMENT ON COLUMN public_mint_audit.dim_employee.emp_section_id IS 'Department / section identifier';
   ```
2. **DataHub UI** (http://localhost:9002) — edit dataset/column documentation after ingest.
3. **DataHub Glossary** — business terms linked to datasets (optional, advanced).

After any change, run `datahub ingest -c datahub_ingestion.yml` again so search indexes update.

### What `schema_pattern` controls

Only schemas in `schema_pattern.allow` are ingested. Tables in other schemas never appear in DataHub for this recipe, so the agent’s DataHub search will not return them.

## 10. Playbook: add a new data source (end-to-end)

Use this checklist when you add a **new warehouse schema** or **switch** the Datamart to a different PostgreSQL source.

### A. Warehouse and application config

1. Ensure the DB user has **SELECT** on the new schema.
2. Set environment variables (or `.env`) used by `backend/app/services/ai_services/datamart/config.py`:

   | Variable | Purpose |
   |----------|---------|
   | `DATAMART_DB_HOST` | Warehouse host |
   | `DATAMART_DB_PORT` | Port |
   | `DATAMART_DB_NAME` | Database name |
   | `DATAMART_DB_USER` / `DATAMART_DB_PASSWORD` | Read-only credentials |
   | `DATAMART_SCHEMA` | Default schema for introspection (e.g. `public_mint_audit`) |
   | `DATAHUB_GMS_URL` | Usually `http://localhost:8080` |

3. Restart the backend (`uvicorn`) so config reloads.

### B. DataHub ingestion

1. Edit `datahub_ingestion.yml` at the repo root:
   - Update `host_port`, `database`, credentials if the **server** changed.
   - Add the new schema to `schema_pattern.allow` (or replace the old schema name).
2. Start DataHub if it is not running (section 2).
3. Run ingestion:
   ```bash
   datahub ingest -c datahub_ingestion.yml
   ```
4. Verify in the UI (http://localhost:9002) or search API that datasets exist for the new tables.

### C. Semantic catalog (`semantic_catalog.yaml`)

File path:

`backend/app/services/ai_services/datamart/semantic_catalog.yaml`

Update four sections for the new domain:

| Section | Purpose | Example |
|---------|---------|---------|
| `topics` | Subject areas + keywords → list of tables | `payroll:` → `dim_employee`, `fact_payroll_detail` |
| `dimensions` | Business terms → `table.column` | `department` → `dim_employee.emp_section_id` |
| `metrics` | Named measures + which tables to use | `average_salary` → `AVG(basic_salary)` on payroll fact |
| `joins` | How facts link to dimensions | `fact_leave_transaction.employee_id = dim_employee.employee_id` |

Keep entries aligned with **real** table/column names in the new schema.

### D. Join hints (optional but recommended)

Edit `backend/app/services/ai_services/datamart/join_hints.py` — `RELATED_TABLE_SUFFIXES` and `_RAW_HINTS` for common join partners when one table is selected.

### E. Validate catalog against live DB

From `backend/`:

```bash
PYTHONPATH=. python tools/sync_semantic_catalog.py
```

- Exit code `0` — catalog table/column refs match the warehouse.
- Exit code `1` — fix `missing_tables` or `unknown_columns` in the YAML.
- Optional JSON report: `PYTHONPATH=. python tools/sync_semantic_catalog.py --json catalog_report.json`

### F. Smoke-test the agent

1. Ask a question that should hit the new tables (e.g. leave, payroll).
2. Check backend logs for `Schema broker: source=broker+datahub` (DataHub contributed table names) or `source=broker` (DataHub empty/off).
3. Confirm generated SQL uses `DATAMART_SCHEMA` and only allowlisted columns.

## 11. Playbook: update an existing data source

| Change | DataHub | `semantic_catalog.yaml` | App config |
|--------|---------|-------------------------|------------|
| New table in same schema | Re-run `datahub ingest` | Add table to relevant `topics`; add `dimensions`/`joins` if needed | No change |
| Column added/renamed/dropped | Re-run ingest | Update `dimensions` / `metrics`; run `sync_semantic_catalog.py` | No change |
| Table renamed | Re-run ingest | Rename table refs in YAML | No change |
| New schema in same server | Re-run ingest with `schema_pattern` | New topics block or new catalog file | `DATAMART_SCHEMA` if switching default |
| New server / database | Update `datahub_ingestion.yml` + re-ingest | Rewrite or duplicate catalog for new model | Update all `DATAMART_DB_*` vars |
| Better search for user phrases | Re-ingest after `COMMENT ON` or UI docs | Add `keywords` / `synonyms` under topics/dimensions | No change |

**Order of operations:** deploy DB change → re-ingest DataHub → update semantic catalog → run `sync_semantic_catalog.py` → restart backend if env changed → test in Datamart chat.

## 12. How the Datamart agent searches DataHub (keyword flow)

Implementation: `backend/app/services/ai_services/datamart/datahub.py`  
Orchestration: `backend/app/services/ai_services/datamart/schema_broker.py`

### Step 1 — Extract keywords from the user question

```python
# Stop-words removed (show, me, the, and, …) — see config.SEARCH_STOP_WORDS
# Tokens length > 2 kept; max 5 keywords (MAX_SEARCH_KEYWORDS)
```

Example question: *“Show top 10 highest paid employees and their job titles”*  
Possible keywords: `paid`, `employees`, `job`, `titles` (stop-words like `show`, `top`, `highest` removed).

### Step 2 — One DataHub search per keyword

For each keyword, the app calls:

```http
POST {DATAHUB_GMS_URL}/api/graphql
```

GraphQL query: `searchAcrossEntities` with:

- `types: ["DATASET"]` — tables/views only, not dashboards or users
- `query: "<keyword>"` — full-text style search in DataHub’s index
- `count: 10` per keyword

Results are **dataset URNs**, deduplicated across keywords, capped at `MAX_CONTEXT_TABLES` (12).

### Step 3 — URN → table short name

URN shape (Postgres platform):

```text
urn:li:dataset:(urn:li:dataPlatform:postgres,warehouse.public_mint_audit.dim_employee,PROD)
```

The broker takes the last segment of the dataset path → `dim_employee` (unqualified table name).

### Step 4 — Merge with other signals (not DataHub-only)

For a **new** chat question, `build_schema_grounding` merges table names from (priority order in merge list):

1. **Semantic catalog** — `resolve_semantics(question).seed_tables`
2. **SQL context** — tables from template SQL / previous turn SQL
3. **DataHub** — tables from URNs above
4. **Warehouse introspection** — all tables in `DATAMART_SCHEMA`, ranked by keyword match on **table name** (`_rank_tables_by_keywords`)

Then:

- Related join partners may be added (`join_hints.py` / catalog joins).
- At most **5 tables** (`BROKER_MAX_TABLES`) are kept.
- **Columns** are loaded by querying PostgreSQL (`introspect_table_columns`), not DataHub.

### Step 5 — What search does *not* do

- It does **not** filter by `DATAMART_SCHEMA` in the GraphQL call — scope is whatever was **ingested**. Keep `schema_pattern` tight so search only indexes intended schemas.
- It does **not** use column descriptions in the current broker path for the allowlist (only table discovery).
- It does **not** replace `semantic_catalog.yaml` — synonyms like “company” → `legal_entity` still need the catalog (or rich DataHub glossary + future code changes).

### Refine / follow-up questions

If the user is only refining SQL (`REFINE_SQL`, `POST_PROCESS_ONLY`, etc.), the broker **skips** DataHub search and uses tables already present in the prior SQL plus related join tables.

## 13. Maintaining `semantic_catalog.yaml` (manual + automated)

### Automated toolchain

| Command | Purpose |
|---------|---------|
| `python tools/semantic_catalog_tool.py validate` | CI check: YAML refs exist in warehouse |
| `python tools/semantic_catalog_tool.py refresh` | **Dry-run**: show what would change |
| `python tools/semantic_catalog_tool.py refresh --write` | Apply safe updates to YAML |
| `python tools/semantic_catalog_tool.py refresh --write --add-dimension-stubs` | Also add stub `dimensions` for new `*_id` / `*_name` columns |
| `python tools/semantic_catalog_tool.py report --json drift.json` | Full drift report |

From repo root after **DataHub ingest** (ingest + refresh + validate):

```bash
# Linux / macOS
./scripts/refresh_datamart_metadata.sh

# Windows PowerShell (reads DATAMART_* from backend/.env; generates datahub_ingestion.generated.yml)
.\scripts\refresh_datamart_metadata.ps1

# Metadata refresh + datamart unit tests (run after agent/catalog/warehouse changes)
.\scripts\after_datamart_change.ps1
```

**When to run:** after any Datamart-related change — warehouse DDL, `DATAMART_*` in `.env`, `semantic_catalog.yaml`, agent prompts, or `schema_pattern` in ingestion. Optional before dev server: `cd backend; .\run-dev.ps1 -RefreshMetadata`.

`sync_semantic_catalog.py` still works; it delegates to `validate`.

### What `refresh --write` updates automatically

- Removes **dimensions** pointing at dropped tables/columns.
- Removes **joins** with invalid tables/columns.
- Drops missing table names from **topics**.
- Assigns **new warehouse tables** to topics (`leave`, `payroll`, `workforce`, …) using name heuristics.
- Appends **join rows** discovered from Postgres **foreign keys**.
- Preserves existing **synonyms** on dimensions that still exist (does not rewrite your wording).

### What you still edit by hand

- Synonyms and keywords for user phrases (“org unit”, “net pay”).
- **Metrics** descriptions (`employee_count`, `top_paid`, …).
- Join **purpose** text (FK auto-joins get a generic purpose).
- `join_hints.py` related-table expansion.

### When to edit manually vs run automation

| Event | Automation | Manual follow-up |
|-------|------------|------------------|
| New table in schema | `refresh --write` adds to a topic | Add keywords/synonyms if needed |
| Column renamed | `refresh` removes stale dimensions | Re-add dimension with new column + synonyms |
| New column only | Optional `--add-dimension-stubs` | Refine stubs or add proper business names |
| DataHub re-ingest | Run `refresh_datamart_metadata` script | Review git diff on YAML |

### HRIS module alignment

`semantic_catalog.yaml` is organized by **HRIS product sections** (employee information, leave, payroll, recruitment, etc.). Each topic has:

- `keywords` — how users ask (works even before mart tables exist, e.g. loan, support)
- `tables` — current mart tables for that module (updated by `refresh --write` when the mart grows)

See `catalog_meta.hris_modules` in the YAML for the full module list.

### Structure (reference)

```yaml
catalog_meta: # documentation only (ignored by agent runtime)
topics:       # HRIS module → keywords + tables[]
dimensions:   # business name → table + column + synonyms[]
metrics:      # metric name → description + tables[]
joins:        # left/right table + columns + purpose
```

### Validation only

```bash
cd backend
PYTHONPATH=. python tools/semantic_catalog_tool.py validate
```

Fix any `missing_tables` or `unknown_columns` before deploying catalog changes.

### Multiple data sources (future-friendly)

Today there is one catalog file for the HR audit mart. If you support multiple schemas/products:

- Option A: separate files (`semantic_catalog_hr.yaml`, `semantic_catalog_finance.yaml`) and select by `DATAMART_SCHEMA`.
- Option B: one file with clearly named `topics` per domain (can grow large).

DataHub can ingest many schemas in one recipe; the semantic catalog should document **business language per domain** you expose in Datamart chat.

## 15. Troubleshooting

| Problem | Cause | Fix |
|---------|-------|-----|
| Port 3306 conflict on startup | Local MySQL using 3306 | Use the patched compose file (section 2) |
| `datahub-mysql-1 is unhealthy` | MySQL still initializing | Wait 20s and re-run `docker compose up -d` |
| `localhost:8080` shows error page | Opening API URL in browser | Use `localhost:9002` for the UI |
| Ingestion returns 0 tables | Wrong schema name in recipe | Check `schema_pattern.allow` in `datahub_ingestion.yml` |
| Agent shows "RELEVANT TABLES: none" | DataHub not running | Start DataHub (section 2), then re-run ingestion (section 4) |
| `permission denied for table` | DB user lacks SELECT grant | Grant SELECT on the target schema to the warehouse reader user |
| SQL uses wrong column name | Catalog synonym outdated | Update `dimensions` in `semantic_catalog.yaml`, run `sync_semantic_catalog.py` |
| DataHub finds tables agent cannot query | Schema ingested but not in `DATAMART_SCHEMA` | Align `DATAMART_SCHEMA` with ingested schema or narrow `schema_pattern` |
